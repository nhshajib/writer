# TypeWit application security audit — 23 November 2026

## Executive summary

Scope: nhshajib/writer at baseline `10374c73c3366bcc5c4093c93d9552d4c31a5271`, production https://typewit.com, and Supabase project jopggisumjlfitapkgjh.
Actual stack: Next.js 15 static export, React 19, TypeScript, Supabase Auth/Postgres/RLS, Deno Edge Functions, Stripe Checkout and signed webhooks. Google Docs worker and Microsoft Word add-in share the session engine.

Four application/dependency findings were identified and fixed: trial checkout races, excessive planner work, fail-open budgets for costly requests, and the Next.js dependency advisory group. One additional configuration finding requires the operator: leaked-password protection is disabled. No Critical or High exploit was confirmed within this audit's scope. This is a scoped code/configuration audit and targeted test, not a guarantee that every vulnerability is absent.

No real writing session, purchase, provider disconnection, customer account change or deletion was used to test. Production HTTP probes used missing credentials, synthetic IDs and an invalid webhook signature. Cross-account authenticated cases ran against the real handlers with fake Supabase transports; no two-account live penetration test was performed.

## Confirmed findings, exploit demonstrations and fixes

### F1 — Medium: canonical-email trial checkout race

**Before:** `trial_available(email)` returned true until a Stripe subscription event recorded the claim. Two independently authenticated accounts using aliases of the same mailbox could both prepare a trial checkout during that window. Per-user checkout locks did not serialize different user IDs.

**Safe PoC:** `scripts/security-trial-race.py` seeds only isolated PostgreSQL fixture accounts and simultaneously invokes the reservation from two aliases. Exactly one receives available, the other busy. Do not run fixture setup against production.

**Fix:** `supabase/functions/billing/index.ts:275` reserves a trial immediately before issuing a new trial checkout. New migration `trial_checkout_reservations` adds a primary-key reservation over normalized email, verified owner identity, expiry, service-only grants, RLS and indexed expiry/owner. The same account can retry. A conflicting alias receives a friendly 409, not a silently paid checkout. Existing claimed trials use the existing paid-checkout path. A reservation lasts 25 hours, beyond Stripe's default 24-hour Checkout expiry; failed requests cannot release a reservation for a still-payable link. Daily housekeeping removes expired bookkeeping. User deletion cascades reservation deletion.

**Tests:** `trial_reservation_database_test.sql`, concurrent PostgreSQL test, added Stripe route test in `stripe_live_checkout_test.ts`. The migration is applied twice in isolated CI to verify rerunnability. Existing fixture transports were extended for the new RPC; assertions were not weakened.

### F2 — Medium: request-driven planner CPU/memory amplification

**Before:** drafting formatting scanned all paragraphs and spans for every emitted step. A supported large rich-text payload could multiply thousands of ranges by thousands of steps. Source length was also rejected only after expensive parsing/compilation.

**Safe PoC:** `security_formatting_test.ts` uses 20,000 synthetic disjoint styles and 2,000 lookups. A second fixture deliberately overlaps 1,000 styles over 1,000 steps and verifies bounded rejection, including a real plan-handler 413 test. The old full scan would inspect tens of millions of ranges. The regression counts range-field reads rather than relying on flaky wall-clock timing. `security_input_test.ts` sends MAX_TEXT_CHARS+1 to the early validator.

**Fix:** `_shared/markdown.ts:109` builds an interval index once; overlapping styles retain original order, paragraph resets and revisited revision ranges. `_shared/drafting.ts:148` reuses that slicer. `_shared/input.ts:8` uses pinned Zod to reject over-limit source before parsing/splitting, including paused replacements. Normal supported formatting and approved text are unchanged. Indexed lookups also enforce a 100,000-range output budget so adversarial overlapping styles cannot produce unbounded output; excessive complexity returns a friendly 413 suggesting larger steps.

**Tests:** the new index is compared against the old scanning algorithm for every nonempty range of a fixture containing overlapping, out-of-order styles and paragraph transitions. All existing formatting, drafting, engine and browser tests remain intact.

### F3 — Medium: costly requests fail open when the rate counter fails

**Before:** the general rateLimit helper intentionally failed open for session-control recovery; creation/planning/provider endpoints also inherited that behavior.

**Safe PoC:** fake hit_rate_limit returns a database error for an otherwise authenticated request. The real plan handler now refuses with 503 before planning/provider work.

**Fix:** `drips/index.ts:114` and related start/plan/check/picker/document call sites, paused planning, and `google-oauth-start/index.ts` opt into failClosed. Billing already did this. Existing control/engine budgets and recovery behavior remain.

**Test:** `security_ownership_test.ts`; existing billing budget tests continue to verify 429 and fail-closed 503 before payment side effects.

## Middleware and validation choices

No Express server exists, so adding Helmet or Express middleware would not protect this static/Deno deployment. Equivalent controls are already in `web/netlify.toml` and `web/vercel.json`: HSTS, nosniff, CSP framing/object/base restrictions, referrer policy and permissions policy. Microsoft Office framing must stay allowed for Word.

`_shared/http.ts` provides the native Deno middleware: origin allowlist, preflight, bounded streamed JSON, nosniff/no-store JSON, request IDs and friendly error mapping. CORS is not treated as authorization; requireUser and RLS provide that. Route-specific server checks remain in place and new source validation uses Zod. No client-supplied price, role or user ID is authoritative.

## Evidence and limitations

- Baseline main CI: https://github.com/nhshajib/writer/actions/runs/43599313180.
- Fresh backend verification: 264 tests passed; deno check/lint/fmt passed.
- Patched frontend baseline: 145 browser tests passed; npm audit found zero vulnerabilities.
- Live probes: admin/config paths 404; unauthenticated controls and checkout 401; forged Stripe event 400; unauthenticated worker 401; attacker origin receives no Access-Control-Allow-Origin.
- Live SQL inspection: all 17 pre-existing public tables have RLS. The public email-domain allowlist is intentionally readable. Owner policies protect user rows. Privileged billing/secret/worker functions are not executable by client roles. The four authenticated SECURITY DEFINER functions are deliberate owner-scoped RPCs.
- Existing service-only tables with RLS and no policies are intentional deny-by-default, not a reason to add permissive public policies.
- Script CSP is report-only while required Next inline scripts, Google Picker and Office hosts are evaluated. Do not turn it into a breaking enforcement policy without staging tests.
- Actual Auth dashboard throttling, exact five-failure behavior, merchant coupon redemption restrictions, full historical secret scanning, arbitrary authenticated live requests and malware scanning were not independently verified. Do not infer these passed from unauthenticated probes.
- A pre-existing migration-history mismatch was found: live session_defaults is recorded as 20261022085807, while the repository contains 20261024000001_session_defaults.sql. Existing applied files/history were deliberately left unchanged. New reservation migration uses the version generated by the production migration tool; see release verification below.

## Rollback

Revert a code fix independently on the audit branch or main and redeploy the affected function from its previous source snapshot. Frontend rollback uses the prior Netlify deploy. Deploy old billing before removing the new RPC/table. Prefer leaving the additive reservation schema in place on a code rollback; it cannot change old billing behavior by itself. Do not drop reservation data while new trial checkout links may still be open. No irreversible customer-data migration is included.
